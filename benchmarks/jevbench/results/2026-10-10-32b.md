# JevBench public cohort — Bernoulli (Qwen2.5-VL-**32B**-Instruct) — 2026-10-10

Production-backbone benchmark run on a **Lambda Cloud H100 PCIe 80 GB** instance (`gpu_1x_h100_pcie` in `us-west-3`). This is the companion to [2026-10-08's 7B dev-tier run](2026-10-08.md) — same cohort, same harness, same adapter commit, same submission SHA (`09e2dd3`), different backbone.

The experimental question was: **"Does 32B meaningfully beat 7B on JevBench?"** — specifically on the hard-tier reasoning categories where the 7B's reasoning ceiling was most visible.

### Why not AWQ

Our documented production target has been `Qwen/Qwen2.5-VL-32B-Instruct-AWQ` (so the 32B weights would fit on a 48 GB L40S alongside KV cache + batching). On the H100 80 GB rental we had enough headroom to run the **unquantized** variant directly, which cleanly sidesteps a stack of AWQ loader issues we hit mid-spike:

- transformers 5.x's AWQ loader routes through `gptqmodel`, which doesn't handle Qwen2.5-VL's partial-quantization scheme (the vision tower stays fp16, only the language model is AWQ-quantized).
- vLLM has native AWQ kernels that would handle it, but vLLM 0.26 was built against CUDA 13 and Lambda's H100 driver tops out at CUDA 12.8.
- `.half()` is blocked post-load on quantized models, blocking a dtype workaround.

Rather than keep chasing the AWQ load, we pivoted to the base 32B model. This separates two measurable questions:

1. **"Does backbone size help?"** ← answered here by comparing unquantized 7B vs unquantized 32B on identical inputs.
2. **"Does AWQ quantization degrade quality?"** ← a separate future measurement, best done when L40S hardware is available (DO quota pending, see `product/research/digitalocean-gpu-options.md`).

## Latency

Each decide call = 2 forward passes through the backbone (reverse debias).

| | 7B on AWS A10G | **32B on Lambda H100** | ratio |
|---|---:|---:|---:|
| original p50 | 92 ms | 519 ms | ~5.6× |
| original p95 | 122 ms | 568 ms | ~4.7× |
| hard p50 | 338 ms | 681 ms | ~2.0× |
| hard p95 | 1634 ms | 2124 ms | ~1.3× |

The latency ratio is **sub-proportional to parameter-count ratio** (32B/7B = 4.6× params, but 5.6× latency on simple prompts, dropping to 2.0× on hard prompts). H100's compute density partially compensates for the parameter growth; the hard-tier ratio is driven by longer input contexts, where our 7B on A10G was already memory-bandwidth bound.

**For publication**: 32B on H100 is still fast enough for interactive demos (<700 ms p50 on hard), well under 1 s. On L40S 48 GB (the eventual production target) latency will be between A10G 7B and H100 32B.

## Reproduce

```bash
# bring up an H100 80 GB (or L40S 48 GB; see note below) with CUDA 12.8+
# bernoulli hard-codes cu130 in pyproject [tool.uv.sources]; patch to cu128 for H100:
sed -i 's/cu130/cu128/g' pyproject.toml
rm -f uv.lock
uv sync --python 3.12 --extra scorer-hf --extra eval --extra serve

# torchaudio ships CUDA-linked by default; force CPU-only to sidestep ABI drift
uv pip install --python .venv/bin/python --index-url https://download.pytorch.org/whl/cpu \
  --force-reinstall --no-deps 'torchaudio==2.11.0'

# start server pinned to 32B
BERNOULLI_MODEL_ID='Qwen/Qwen2.5-VL-32B-Instruct' \
BERNOULLI_MODEL_REVISION='7cfb30d71a1f4f49a57592323337a4a4727301da' \
BERNOULLI_DTYPE=bfloat16 \
BERNOULLI_SCORER=hf \
  uv run --no-sync uvicorn bernoulli.server:app --host 0.0.0.0 --port 8000

# run cohort
for split in original easy hard; do
  uv run --no-sync python -m benchmarks.jevbench.run \
    --tasks benchmarks/jevbench/upstream/datasets/public/$split.jsonl \
    --results benchmarks/jevbench/results/$split-<date>-32b.jsonl \
    --endpoint http://127.0.0.1:8000
done

# summarize
for split in original easy hard; do
  PYTHONPATH=benchmarks/jevbench/upstream uv run --no-sync python -m jevbench.cli summarize \
    --tasks benchmarks/jevbench/upstream/datasets/public/$split.jsonl \
    --results benchmarks/jevbench/results/$split-<date>-32b.jsonl
done
```

**Note on hardware substitution**: on L40S 48 GB (the eventual production target), the base 32B model (65 GB fp16) **does not fit**. You'd use the AWQ-quantized variant there instead — but vLLM 0.26+ with cu128 is needed to handle Qwen2.5-VL-AWQ's partial-quantization scheme; the transformers path via gptqmodel does not work. See the "Why not AWQ" section above for the full stack.

## One-sentence takeaway

**Backbone size matters a lot on hard-tier reasoning (+18 pp on hard, +33 pp on tradeoff/multi_hop/long_policy; brier halved); matters a little on standard-tier (+2.8 pp); matters zero on easy (both at 100%)** — which is the pattern you'd predict and gives us a clean justification for the M4e production step-up whenever the infra is available.
