### Where provisioning hung (the real blocker)
`just serve-provision` ran sync + model-pull + started `docker build`. Then stayed in `docker build` with **no new output for over an hour**. Killed. Root cause almost certainly the vLLM base image pull (~10 GB) stalling on g5.xlarge's single-stream bandwidth, or Docker's own storage layer. The architectural choice to use Docker — specifically, with Docker's data-root on NVMe which is wiped on stop/start — means **every stop/start costs a full base-image re-pull**.

## The pivot to make tomorrow

User flagged the real problem: rebuilding a Docker image on every provision is wasteful. Three options discussed; **recommendation is to skip Docker for the dev-tier endpoint**:

- **Option A (push to GHCR, pull on start)**: doesn't save bytes; same ~10 GB over the wire on every cold start. Not worth the registry-auth setup.
- **Option B (move Docker data-root from NVMe → EBS)**: image persists across stop/start, so one-time pull. But tight on 80 GB EBS (vLLM image 10 GB + Qwen weights 15 GB + venv 3 GB + OS + logs). Would need to bump EBS to 120 GB (~$5/mo).
- **Option C (skip Docker, run uvicorn via systemd)** ← **recommended**:
  - uv venv on EBS persists across stop/start.
  - `uv run uvicorn bernoulli.server:app --host 0.0.0.0 --port 8000` as a systemd unit; `--restart=always` style but via systemd `Restart=always`.
  - Cold start = EC2 boot (~90s) + systemd + vLLM/Qwen load (~90s) = ~**3 min**, vs the 10+ min Docker route.
  - `BERNOULLI_API_KEYS` goes in the systemd unit's `Environment=` line.
  - Dockerfile stays in the repo untouched — still the right production path when image-based deployment matters.
